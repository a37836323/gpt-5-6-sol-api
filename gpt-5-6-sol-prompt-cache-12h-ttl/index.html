gpt-5.6-sol 提示缓存设置：用 ttl 选 30 分钟或 12 小时

OpenAI 在 2026-10-20 的更新日志里宣布 API 可以选择 12 小时提示缓存。对 gpt-5.6-sol 这类 GPT-5.6 及之后的模型，缓存时长由 prompt_cache_options.ttl 控制：默认 30m，在 Responses API 里可以设为 12h；早期模型用的 prompt_cache_retention（in_memory、24h）不是这一代模型的设置方式，官方迁移建议是把它换成 prompt_cache_options.ttl。下面按官方提示缓存指南逐项说明怎么设、什么情况下不会生效、怎么从返回的 usage 里确认。

官方改了什么：GPT-5.6 及之后的缓存时长参数

OpenAI 更新日志 2026-10-20 的条目写明：现在可以在 API 中选择 12 小时提示缓存，适用于 v1/responses，用来让共享的指令、工具和上下文在缓存里保留更久，请求之间隔几个小时也能按缓存输入计费。

提示缓存指南把规则按模型分成两套。GPT-5.6 及之后的模型：在 Responses API 里设置 prompt_cache_options.ttl 选择最短缓存时长，可选 30m（默认）和 12h，也可以用 prompt_cache_breakpoint.ttl 给单个断点单独指定时长；填写不支持的值会返回 400 invalid_request_error。

早期模型：使用 prompt_cache_retention，取值 in_memory 或 24h。指南列出的支持 24h 的模型是 gpt-5.5、gpt-5.5-pro、gpt-5.4、gpt-5.2、gpt-5.1 系列、gpt-5 系列和 gpt-4.1，其中没有 GPT-5.6 系列。指南还说明新设置不会改变早期模型的 prompt_cache_retention 参数，并在迁移一节建议把 prompt_cache_retention 换成 prompt_cache_options.ttl。

所以从 gpt-5.5 之类的旧模型切到 gpt-5.6-sol 时，原来写的 prompt_cache_retention: 24h 不能当成 24 小时缓存来理解，应该改为 prompt_cache_options.ttl，并且只在 30m 和 12h 里选。

怎么设置：请求级 ttl、断点和缓存模式

最简单的写法是在 Responses 请求体顶层加上 "prompt_cache_options": {"ttl": "12h"}，把这次请求写入缓存的默认时长设为 12 小时；不写时就是默认的 30m。

需要不同内容用不同时长时，可以在输入消息的内容块上加 prompt_cache_breakpoint。指南的示例是：请求级设为 {"mode": "explicit", "ttl": "30m"}，在一段长期不变的 developer 共享资料上放 {"mode": "explicit", "ttl": "12h"} 的断点覆盖默认值，会话上下文用不带 ttl 的断点继承 30m，最后的当前问题不放断点、不写缓存。

prompt_cache_options.mode 有 implicit 和 explicit 两种。implicit 模式下，OpenAI 会在最新一条符合条件的消息末尾自动放一个断点，符合条件的是用户消息、连续工具返回里的最后一条、开头 developer 消息块里的最后一条。explicit 模式只认你自己放的断点；指南特别提醒，explicit 模式下一个断点都没放，这次请求就不使用提示缓存，也不产生缓存写入。

其他限制：每个请求最多产生 4 次缓存写入，implicit 模式的自动断点占其中 1 个；顶层 instructions 里不能放显式断点；additional_tools 输入项目前不接受 prompt_cache_breakpoint。12h 在指南里只写了 Responses API，需要 12 小时缓存时请走 /v1/responses。

什么时候值得设 12 小时

按更新日志的说法，12h 适合同一段指令、工具定义和上下文会被反复使用、但请求之间间隔可能超过默认 30 分钟的场景，例如每隔几小时跑一批任务、复用同一份长系统提示的工作流。请求本来就很密集时，默认 30m 往往已经够用。

计费上要注意：对 GPT-5.6 及之后的模型，缓存写入本身按高于普通输入的费率计费，12h 写入的费率又高于 30m 写入；读取缓存的费率两种时长相同。另外 prewarm（只预热缓存、不生成输出）写入的 token 也按所选时长的写入费率计费。具体单价以 OpenAI 官网价格页和 OpenLux 价格页为准。

指南还写明 12h 是最短保留时长，不是删除期限，OpenAI 可能保留得更久，但这不改变数据保留上限；ZDR 组织同样可以使用全部提示缓存功能。

缓存有最低长度：GPT-5.6 及之后的模型最少 1,024 个 token 才会缓存，OpenAI 隐藏的系统 token 不计入。前缀不到这个长度，设 12h 也不会有缓存写入。

设了 12h 还是没命中：常见原因

前缀没有完全一致。指南写明缓存复用要求整个渲染后的前缀都匹配；工具的名称、描述、schema、顺序有任何变化都算前缀变化；文本、图片、文档也都在缓存内容里。时间戳、请求 ID 这类每次都变的内容要放到最后，不要放进共享前缀。

改写了已有消息。在已有消息后面追加内容而不是新增一条消息，也可能导致前面缓存的前缀无法复用；指南建议保留完整的对话历史，按追加的方式更新工具。

切到 explicit 模式但没放断点，或者只在顶层 instructions 里想放断点。这两种情况都不会产生对应的缓存写入。

把 prompt_cache_key 当成命中开关。对 GPT-5.6 及之后的模型，指南说明这个键是可选的，只用来按客户或用户分开缓存统计、防止跨用户探测缓存，不承担早期模型那种改善路由的作用。想定位具体是哪一处变了，可以用官方的 Prompt Cache Diagnostics（2026-09-08 起在 Responses API 对 GPT-5.6 及之后的模型正式可用）。

怎么验证 12 小时缓存已经生效

看返回的 usage。指南列出的字段是 usage.input_tokens_details 下的 cached_tokens 和 cache_write_tokens，写入还会在 cache_write_tokens_details 里拆成 ttl_30m_tokens 和 ttl_12h_tokens，两者之和等于 cache_write_tokens；cached_tokens 只统计按读取计费的部分，不含按写入计费的 token。

成功标准分两步：第一次带 ttl: 12h 发出一个前缀超过 1,024 token 的请求，ttl_12h_tokens 应大于 0；之后用完全相同的前缀再发请求，cached_tokens 应大于 0。如果 ttl_12h_tokens 一直是 0、写入都记在 ttl_30m_tokens 里，说明 12h 设置没有作用到这次请求，先检查参数位置、端点是不是 /v1/responses、是否处在 explicit 模式且断点没覆盖到。

长期看命中率，指南给的算法是累计 cached_tokens 除以累计输入 token，并结合延迟和费用一起观察，平台后台也有 Prompt Caching 仪表盘可以看。

如果参数写错，例如沿用旧习惯把 ttl 填成 24h，官方写明不支持的值会返回 400 invalid_request_error，按上文改成 30m 或 12h 即可。

通过 OpenLux 中转调用 gpt-5.6-sol 时怎么做

gpt-5.6-sol 目前在 OpenLux 价格接口中在售，列出的端点类型包括 OpenAI 兼容的 Chat Completions 和 Responses。需要 12 小时缓存时，Base URL 填 https://api.openlux.ai/v1，请求 /v1/responses；Key 在 OpenLux 控制台的「令牌」页创建。

建议先请求 /v1/models 确认地址和 Key 正确（返回 401 说明 Key 错或没带上），再按上一节的两步法看 usage 字段。本站没有用真实请求逐项核实中转对 prompt_cache_options 和断点参数的处理，是否生效以返回的 usage 为准；费用以 OpenLux 价格页和控制台账单为准。
