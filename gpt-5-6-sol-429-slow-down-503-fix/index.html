gpt-5.6-sol 报 429 slow_down 或 503 server_is_overloaded：怎么区分和处理

OpenAI 在 2026-09-02 的更新日志中调整了错误返回：流量增长过快会返回 429，错误码为 slow_down；模型临时过载会返回 503，错误码为 server_is_overloaded。两种情况都可能带 Retry-After 响应头。本页依据官方错误码文档、限流指南和 openai-python 说明，整理调用 gpt-5.6-sol 时如何区分这几类错误、哪些可以重试、哪些重试也没用。

先看 error.code，不要只看 HTTP 状态码

同样是 429，原因可能完全不同。官方错误码文档列出的 429 包括：请求太快触发的普通限流（Rate limit reached）、错误码为 slow_down 的流量增长过快、预付额度用完的 credit_balance_exhausted，以及组织或项目达到花费上限的 organization_spend_limit_exceeded、project_spend_limit_exceeded、organization_usage_limit_exceeded。503 中错误码为 server_is_overloaded 的情况，表示所请求的模型暂时过载。

所以排查第一步是把响应体里的 error.type 和 error.code 记下来。官方特别提示：额度类错误要看 error.code，因为 error.type 仍可能是 insufficient_quota。用 openai-python 时，429 会抛出 RateLimitError，503 会抛出 InternalServerError，两者都要捕获并检查错误码，不能用同一套逻辑处理。

建议同时记录发生时间（含时区）、模型名 gpt-5.6-sol、调用的接口（Responses 或 Chat Completions）和请求 ID。openai-python 的成功响应可以读 _request_id，失败时捕获 APIStatusError 后读 request_id。

429 slow_down：没超过 RPM、TPM 也可能出现

官方说明 slow_down 的含义是请求速率增长得太快，并明确写到：即使流量仍在每分钟请求数（RPM）和每分钟 token 数（TPM）限额之内，也可能收到这个错误。因此看到 slow_down 时，不要只去对照限额表，而要看最近是否突然放量，例如批量任务刚启动、并发数一下子调高、或者多个服务同时开始调用。

官方给的处理办法有四条：有 Retry-After 响应头就按它等待；没有这个响应头就拉长重试间隔并加随机抖动；先把速率降下来，再逐步加回去；尽量让流量保持平稳。官方还给出一个经验值：当输入流量达到每分钟 100 万 token 以上时，每 15 分钟增幅不超过 50%，具体阈值因模型和当时情况而异。

实际操作上，可以把任务改成分批启动，用队列控制并发上限，按时间段逐级提高并发，而不是一次性把所有任务同时发出。

503 server_is_overloaded：模型临时过载

server_is_overloaded 的错误类型是 service_unavailable_error，官方解释为所请求的模型暂时过载。处理方式是遵守 Retry-After 后再重试；如果持续出现，到 status.openai.com 查看服务状态。

官方在更新日志里说明，把 slow_down 和 server_is_overloaded 分成两个错误码，就是为了让应用区分「流量增长过快」和「模型临时过载」。对 503 的合理做法是设置有上限的重试，超过上限就把任务放回队列稍后处理，并在日志里单独统计 503 的出现时间，便于和服务状态页对照。普通的 500 服务器错误，官方建议是稍等后重试并查看状态页。

额度和花费类 429：重试不会恢复

官方错误码文档写明：重试计费、花费上限或额度类错误，不会恢复 API 访问。credit_balance_exhausted 需要先补充额度；organization_spend_limit_exceeded 和 project_spend_limit_exceeded 需要调高或取消上限，或者等每月重置，其中项目级上限只影响该项目；organization_usage_limit_exceeded 是 OpenAI 为组织设定的限制，与自己设置的花费上限不同，需要申请提高或联系支持。

因此重试逻辑里应该把这些错误码排除在外：遇到就停止该任务、发出告警，由人处理账户问题。否则自动重试只会持续制造失败请求。

重试怎么写才不会放大问题

第一，遵守 Retry-After。官方要求：响应带有 Retry-After 时，至少等待它指定的时长；没有这个响应头或取值无效时，使用带随机抖动的指数退避，并限制重试次数和总重试时间。如果要求的等待时间超过你能接受的上限，应把请求延后处理，而不是提前重试。

第二，失败的请求也计入每分钟限额。官方限流指南提醒，不停地重发同一个请求并不能解决问题，反而会继续消耗限额。

第三，不要在 SDK 重试之外再叠一层重试。openai-python 默认会对连接错误、408、409、429 和 5xx 自动重试 2 次，并使用较短的指数退避。可以用 OpenAI(max_retries=0) 关闭 SDK 重试、改由自己的队列统一控制，也可以用 client.with_options(max_retries=5) 单独调整某次调用。官方错误码文档还提到，当服务端要求的等待时间较长时，Python 库在某些版本中可能不再自动重试，应用层的重试要尊重原始等待时间。流式输出读取过程中的失败不会被自动重试，因为重放请求可能产生重复输出。

第四，把 max_tokens 设在接近实际需要的值。限流指南说明，限额按 max_tokens 与按请求字符数估算的 token 数中较大的一个计算，设得过大会更快用完 TPM。

通过中转调用时，先确认错误来自哪一层

如果你通过 OpenLux 这类中转平台调用 gpt-5.6-sol，返回的 429 或 503 可能来自平台本身（例如账户额度、分组或平台侧的频率限制），也可能来自上游服务。本页不保证平台会原样透传 slow_down 或 server_is_overloaded 错误码，x-ratelimit 系列响应头和 Retry-After 也不一定出现，一切以你实际收到的响应为准。

排查时先保存完整的错误响应体和响应头（注意去掉 API Key），再到控制台查看对应时间的使用记录和账户额度。如果错误体中没有 slow_down 或 server_is_overloaded，就不要套用本页对应的结论；带着时间、模型名和错误内容联系平台客服核对，不要发送完整密钥。

处理完成后如何确认已经恢复

可以按以下标准确认：降速或重试后，同一批任务不再出现 slow_down；503 只在个别时段零星出现，并能在 Retry-After 指定时间后成功；额度类 429 在补充额度或调整上限之后不再出现；日志里每个失败请求都有错误码、时间和请求 ID，重试次数没有超过设定上限。

直连 OpenAI 时，还可以查看响应头 x-ratelimit-remaining-requests 和 x-ratelimit-remaining-tokens，确认剩余额度不再贴近 0。官方限流指南说明，限额按组织和项目设定，并且随模型不同而不同；直连时，对于不需要实时返回的任务，可以考虑 Batch 接口：gpt-5.6-sol 的模型页列出了 Batch，限流指南说明 Batch API 不占用同步调用的限额。通过中转调用时，是否提供 Batch 以平台说明为准。
